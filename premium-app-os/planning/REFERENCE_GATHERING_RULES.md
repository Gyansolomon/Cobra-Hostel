# Reference Gathering Rules

References help create better plans. They are for learning, not copying.

## What to Gather

For each project, gather references for:

- product model
- onboarding
- core user flow
- listing/search
- detail page
- forms
- dashboard/admin
- empty states
- error states
- pricing/payments if relevant
- maps/charts/files if relevant

## Where to Look

Use current and relevant sources:

```text
Mobbin
App Store screenshots
Google Play screenshots
Figma Community
Dribbble
Pinterest
Tailwind UI
shadcn/ui examples
Radix examples
Tremor examples
real competitor products
official docs for component libraries
```

If recommendations may be outdated or paid, check current sources before advising the user.

## What to Extract

For each reference, record:

```text
Reference:
Source/link:
Relevant page/screen:
What to learn:
What not to copy:
Cost/license concern:
```

Extract:

- layout logic
- content hierarchy
- navigation pattern
- component grouping
- spacing rhythm
- imagery treatment
- motion behavior
- empty/error state pattern

Do not copy:

- brand identity
- exact layout
- protected illustrations
- proprietary assets
- trademarked marks
- paid assets without a license

## Page-Level Reference Rule

Do not say "use Airbnb" or "use Apple" broadly.

Say:

```text
Use Airbnb's listing detail structure as inspiration for trust signals, image gallery, sticky CTA, and review hierarchy. Do not copy branding or exact layout.
```

## User Assistance Rule

Ask the user for references when:

- brand taste matters
- the app is in a niche domain
- local cultural context matters
- real competitors are known by the user
- visual direction is unclear

If the user has no references, propose 3-5 likely references and explain why.
